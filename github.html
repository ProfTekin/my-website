GitHub: build together.

Keep a useful history, share the work, and understand what publication actually means.

Git keeps history. GitHub helps you share it.

TermMeaning

CommitA recorded snapshot of selected changes with a message.
CloneMake a local copy of a repository and its history.

Edit locally → Commit → Push to GitHub

Before the next edit: fetch and pull your partner’s changes.

Create your shared repository

  1. Sign in with your own school-approved GitHub account. Do not share a password.
  2. Use the + menu → New repository. Choose a clear name such as alpine-coffee-prototype.
  3. Use the teacher-approved visibility. Prefer a private repository while developing; do not publish confidential or personal information. Add a README and create the repository.
  4. Open Add file → Upload files. Upload your HTML, CSS, JavaScript and images with their folder structure intact.
  5. Write a meaningful message such as “Add initial four-page structure” and commit the changes. Check that the files appear in the repository.

A browser upload records a commit directly on GitHub. Editing a local clone uses a local commit followed by a push. These are two workflows, not extra steps that always happen together.

Collaborate without overwriting each other

  1. Repository owner: open Settings → Collaborators (sometimes shown under access settings), add your partner’s verified GitHub username, and send an invitation. The partner accepts it.
  2. Agree on a small task for each partner. Both must program and understand the whole site. Avoid editing the same lines at the same time.
  3. Optional GitHub Desktop workflow: File → Clone repository, choose the shared project, then open that local folder in your editor. GitHub Desktop is an optional Windows/macOS tool; Linux users can use the browser or a teacher-approved Git client.
  4. Before editing, fetch and pull the latest changes. Save your own uncommitted work deliberately before switching tasks or integrating updates.
  5. Edit and test locally. In the Changes view, inspect the diff, select the intended files, enter a specific summary, and commit to the current branch.
  6. Push origin so your partner receives the commit. Your partner fetches/pulls before their next edit.
  7. Review the History view together. Use meaningful commits such as “Fix mobile menu keyboard behavior”, not “stuff”.
A commit count alone does not measure contribution. Discuss decisions, test each other’s changes and document individual understanding.

Branches and a first merge conflict

For separate work, create a branch, commit and push it, then open a pull request on GitHub. Your partner reviews the changes before merging. If Git cannot combine edits to the same area, it reports a conflict. It does not know which version you intended.

  1. Read both versions with your partner. Do not simply delete one person’s work.
  2. Use the conflict editor or your Git client to keep the intended combined result. Remove conflict markers from the actual file.
  3. Test the merged page, mark the conflict resolved, then commit and push. Ask your teacher for help before discarding work.

Optional publication: GitHub Pages

Stop before making anything public: ask your teacher. Public publication is optional. Ordinary GitHub Free personal repositories generally must be public to use Pages. Do not assume a private repository makes its Pages site private.
  1. Obtain teacher approval. Check permissions, credits, identifying information and the unofficial-prototype label.
  2. Prepare the repository: for main / (root), index.html must be at the repository root, next to your stylesheet and script, with images in their relative folder.
  3. Open repository Settings → Pages.
  4. Under Build and deployment → Source, select Deploy from a branch.
  5. Choose main and / (root). Alternatively, use /docs only if index.html and all site files are inside that folder. Basic branch publishing allows root or /docs, not an arbitrary folder.
  6. Save the settings. Wait for the deployment to finish; inspect the repository’s Actions tab if it fails.
  7. Open the site URL displayed in Pages settings. A project site normally uses https://USERNAME.github.io/REPOSITORY/. The repository’s github.com URL is not the website URL.
  8. Click every link and test your CSS, images and JavaScript on the hosted site.
  9. To update it, commit and push revised files to the selected source. Deployment and browser caches can delay what you see.

Official publishing-source instructions · Create a Pages site

Pages serves static HTML, CSS and JavaScript. It does not run a custom PHP backend or server-side database. A classroom demonstration creates no obligation to host a company website permanently. Any official company use needs separate arrangements and review of the host’s terms.

When the hosted site looks wrong

SymptomCheck
404 / file not foundIs index.html in the configured root or docs folder? Is it accidentally inside one extra folder?
Wrong page or repository listingUse the published Pages URL, not the GitHub repository URL.
Missing CSS, JS or imagesCheck relative paths, filename extensions and exact capitalization. Coffee.svg and coffee.svg may differ.
No deploymentCheck Pages source, branch, folder and Actions result. Make sure the branch exists and contains your files.
Old versionCheck that your commit was pushed and deployment finished. Reload without cache after that.
Only subpages failCheck every link relative to that page. Do not use absolute local disk paths or root-leading / paths in this portable project.

For this handbook, upload the contents of the extracted webdev-lab folder so index.html is at the repository root. Do not upload only the ZIP.

What Is a Content Management System?

A CMS lets users create, edit and organize website content through an interface. Companies use it when staff need to update pages without editing HTML files directly. WordPress is one example.

Hand-coded static websiteCMS-managed website
You edit HTML, CSS and JavaScript files.Editors typically use forms or a visual editor in a dashboard.
Content is stored in files for this project.Content is often stored in a database or another managed content store.
Shared design lives in your stylesheet.Themes or templates control shared presentation.
Repository access governs who can change source.Roles such as administrator, editor and author control permitted actions.
A static host can serve the finished files.Hosting needs depend on the CMS; some CMS workflows export static files.
Updates require editing and publishing your files.Authorized staff can draft, review and publish through the CMS.

A dashboard is the management area for pages, media, settings and users. Give people only the permissions they need. This project still uses HTML, CSS and JavaScript. This introduction does not replace practical CMS teaching and does not require installing WordPress.
